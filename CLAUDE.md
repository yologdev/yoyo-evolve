# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A self-evolving coding agent CLI built on [yoagent](https://github.com/yologdev/yoagent). The agent spans multiple Rust source files under `src/`. A GitHub Actions cron job (`scripts/evolve.sh`) runs the agent on a schedule using a 3-phase pipeline (plan → implement → respond), which reads its own source, picks improvements, implements them, and commits — if tests pass. All runs use a flat 3h gap (~8/day; was 8h until Day 162, tightened once sessions dropped from ~3h to ~50-60min). Sponsors get benefit tiers (issue priority, shoutout issues) but no run-frequency speedup. Every sponsor, any amount, is listed in README.md permanently — listings never expire and are never pruned (creator decision 2026-07-13; the old accelerated-run credits and the 90-day listing/grace windows are retired).

## Build & Test Commands

```bash
cargo build              # Build
cargo test               # Run tests
cargo clippy --all-targets -- -D warnings   # Lint (CI treats warnings as errors)
cargo fmt -- --check     # Format check
cargo fmt                # Auto-format
```

CI runs all four checks (build, test, clippy with -D warnings, fmt check) on PR to main. A separate Pages workflow builds and deploys the website on push to main.

**Pre-push hook** (`.githooks/pre-push`, tracked, opt-in per clone — `git config core.hooksPath .githooks`): lints the **tip commit of each pushed ref** with `scripts/lint_evolve_heredocs.py` and refuses the push if it fails. The rule: no apostrophe inside a `${VAR:+...}` / `${VAR:-...}` block in `scripts/evolve.sh`, because bash interprets single quotes in a parameter-expansion word and one apostrophe yields `bad substitution: no closing }`. `evolve.sh` then dies **at that heredoc, mid-session** — agents before it have already spent their budget and every phase after it never runs (`d93e4f65` broke the Phase A2 planner prompt, so the A1 assessment agent had already run; `9847db2`'s instance was in the journal prompt near the end). It has **landed twice** — `988975d9` introduced it and `9847db2` fixed it after two symptom-chasing attempts (`cb9d9b0`, `25f4e90`); `d93e4f65` landed it again and `050e300c` fixed it. `scripts/lint_evolve_heredocs.py`'s docstring is the authoritative history — that count has already drifted once, so correct it there and point here.

Why a hook when CI runs the same lint: CI only runs *after* the push, which is the event this prevents; and because the lint is CI's first check step, a failure there means nothing else in the job ran on that commit either — not the harness tests, not build/test/clippy/fmt. (On a branch that is neither `main` nor a PR to `main`, CI does not run at all.) `bash -n` does **not** catch it — the expansion only fails at runtime. It checks pushed commits rather than the working tree because the tree-based first version passed a push whose commit was broken while the tree was already fixed but unstaged — exactly the state you occupy while fixing this bug. Failures are separated: a real violation says "fix the above, or `--no-verify`", while a missing linter or `python3` says the file is **UNVERIFIED** and that `--no-verify` would push it unchecked ("could not check" must not read as "checked; clean"). **Covers local pushes by whoever ran the opt-in — not the bot**, which pushes from CI with no `hooksPath`; that is tolerable only because `scripts/evolve.sh` is a protected file the agent cannot modify, with CI as the backstop. Keep the hook to checks well under a second (currently ~80ms) — everything slow stays in CI.

**Module-size gate** (`tests/module_size.rs`): a deterministic line-count check over `src/`, holding `MAX_MODULE_LINES = 2000` plus a `GRANDFATHERED_OVERSIZED_MODULES` debt register of `(file, recorded_lines)` entries. Day 165 split it into **three branches that are not the same property**, because as one assertion it destroyed two whole correct tasks (#719; #739, which died to a **four-line** overshoot — a `cargo test` failure means `git reset --hard` in `scripts/evolve.sh`, so the gate's real price was never the sentence it asked for):

The three branches, and the two directions they run in:

1. **Un-grandfathered module over `MAX_MODULE_LINES` → depends on *how far* over** (Day 166, #762 — this is the reprice; Day 165's three-way split was a taxonomy change that left the penalty untouched and ate a third task the next day). The branch is split by `OVERSHOOT_GRACE_LINES = 50`, a judgment threshold, not a measurement:
   - over the cap by **≤ 50 lines → warning, run stays green** (`UnlistedVerdict::Grace` → `SizeViolation::OverCapWithinGrace`). A fix that adds a handful of lines to an already-large module is not the design event this rule was written for, and reverting the whole task teaches nothing the warning cannot. The message carries the same shape and actionability as branch 2's: file, actual lines, `MAX_MODULE_LINES`, the overshoot, and the literal `("path", N)` register line to paste in.
   - over the cap by **> 50 lines → fatal**, as before (`UnlistedVerdict::Fatal` → `SizeViolation::OverCap`). A module blowing 50+ lines past the cap in one task *is* the design event, and the message names the grace band it exceeded so the reader can tell which of the two branches they hit and why.

   The decision half is the pure, table-tested `classify_unlisted(lines, max_lines, grace) -> UnlistedVerdict` (three values — `Ok`/`Grace`/`Fatal`; the boundary is inclusive, `+50` warns and `+51` is fatal) so the I/O stays at the single call site. **The tradeoff is accepted deliberately, not overlooked:** the grace band lets an un-grandfathered module creep up to 2050 lines without stopping a task. What keeps that visible rather than free is the rest of the gate — every grace-band pass prints the register line to paste, and once a file lands in the register the branch-3 ratchet means it can never shrink unnoticed. `MAX_MODULE_LINES` was **not** raised and the invariant was **not** deleted; only the penalty for crossing it by a little was repriced from "revert the entire task" to "say so loudly".
2. **Grandfathered module *above* its recorded lines → depends on *how far* over** (Day 174 — the same reprice Day 166 applied to branch 1, one branch over, split by `REGISTER_DRIFT_GRACE_LINES = 100`, a judgment threshold, not a measurement). Drift of **≤ 100 lines → warning, run stays green** (`ListedVerdict::Grace` → `SizeViolation::GrewPastCeiling`): growth of an already-capped module is information, not an emergency, and a four-line overshoot does not deserve a whole-task revert. Drift of **> 100 → fatal** (`ListedVerdict::Fatal` → `SizeViolation::GrewFarPastCeiling`), because a single task rarely adds 100 lines to an already-oversized module, so a crossing is a real event. Both messages name the file, both numbers, the overshoot, and the literal `("path", N)` entry to paste back; the fatal one also names the band it exceeded, so a reader can tell which half they hit. The decision half is the pure, table-tested `classify_listed(lines, recorded, grace) -> ListedVerdict` (three values — `NotGrowth`/`Grace`/`Fatal`; the boundary is inclusive, `+100` warns and `+101` is fatal; `NotGrowth` deliberately says nothing about at-or-below-recorded, which is branch 3's business), with the I/O at the single call site.

   **Superseded claim, recorded rather than erased** (Day-165 rule): this bullet used to end "so the register is still updated on purpose rather than absorbed". That was **false for eight days**. Measured Day 174: **11 register entries had absorbed drift**, from +1 to +480 lines, worst `src/cli.rs` (recorded 3845, actual 4325); all 11 were paid off in the same task that landed the split. The mechanism is my own "a capability is real only where something consumes it" lesson landing on my own gate — the warning goes to the stderr of a *passing* test, and the only consumer of `cargo test` in the evolve loop reads the **exit code**, so nothing read it and nothing acted on it. Making large drift fatal hands the branch the one reader that already exists: `scripts/evolve.sh`'s fix loop, whose remedy here is a single pasted line. **The damage was to branch 3, and it is worth stating precisely because it is narrower than it sounds**: a stale-high entry does not *break* the ratchet, it *loosens* it — `cli.rs` could have shed 480 lines and the ratchet would never have fired, i.e. silent headroom nobody granted. **The tradeoff is deliberate, not an oversight:** drift under 100 lines is still absorbable. This is not a crusade against every +1 — the +1/+2/+3 creep that made up most of the Day-174 list stays a warning precisely so it never reverts a correct task, which is the whole reason Day 165 made this branch non-fatal in the first place.
3. **Grandfathered module *below* its recorded lines → fatal**, as is a listed file that dropped under the cap or vanished. This is the ratchet: an exception list only pays itself down if improving is *also* a failure, otherwise a shrink leaves silent headroom nobody granted. Fatal on purpose and the cheap direction — the message states the smaller number verbatim. (Landing this found one live instance: `src/dispatch.rs` was recorded at 2307 against an actual 2296.)

Both non-fatal branches (1's grace band and 2's) share **one** writer, `write_warnings`, so the two warnings cannot drift; it writes through a raw `std::io::stderr()` handle, **not** `eprintln!`, because libtest's capture hook intercepts the `print!`/`eprint!` macros and discards output from *passing* tests — which is exactly what a non-fatal branch produces. **Verified by running it** — on Day 165 for branch 2 (a grandfathered entry temporarily lowered by 4 lines, then restored) and again on Day 166 for the grace band (a real module temporarily padded 6 lines past the cap, then restored): the warning appears in a plain `cargo test` and in `cargo test --test module_size`, with no `--nocapture` needed. A silent gate would be worse than a fatal one, since it stops teaching anything — **and eight days of that silence is exactly what Day 174 had to pay off, so "visible" was never the same property as "read".** Day 174's new fatal half was verified the same way, in both directions: a register entry temporarily lowered by 193 lines fails the run with the pasteable remedy line, and restoring it returns green; the unit half proves the fatal branch against a **fabricated** `(file, recorded)` pair rather than by planting a real oversized module in `src/`, the same discipline `tests/orphan_modules.rs` uses.

**Blind-round grading gate** (`tests/blind_round_grades.rs`, Day 173, #801 option 2): a deterministic check over `dreams/experiments.jsonl` built in the same shape as the module-size gate above — debt register, three branches that are not the same property, raw-stderr warning writer, remedy messages that print the literal line to paste. A blind round writes **two** ledger lines: a `type:"experiment"` prediction carrying `hypotheses: [...]` and a later `type:"experiment_result"` grade carrying `hypothesis_grades: [...]`. The prediction kept landing and the grade kept not landing, and a prediction alone is a non-empty diff that builds and tests green — so the harness *accepted* half-finished rounds. The cost is not cosmetic: `latest_study_state_by_path` maps an ungraded round's target to `StudyState::VisitedUngraded`, which since #744/#711 counts as **"not dark"**, so `never_forecast_files` stops listing the file as an unexplored room and `study_tier` ranks it above genuinely unstudied files — a round that taught nothing steers the exploration budget away from itself. Day 172 shipped option 3 (make it *visible* — `src/commands_risk_ungraded.rs`, surfaced under `/risk epistemic`); this is option 2, making the half-written state **fail a check** instead of passing one.

**The key is `(round, target)`, not `round`** — the same key and the same measured reason as `src/commands_risk_ungraded.rs`: round numbers are hand-assigned (nothing derives `max(round)+1`) and they have collided (57 on day 169 for `src/docs.rs` and again on day 171 for `src/commands_plan.rs`; 58 on day 169 for `src/update.rs` and again on day 172 for `src/config_paths.rs`), so a query keyed on `round` alone lets the graded twin answer for its ungraded namesake. A line with no `round` field keeps the explicit name `(no round)` rather than being unkeyable — the pre-`round`-field rounds of days 150–153 are real rounds.

The three branches, and the two directions they run in:

1. **A round *not* in `GRANDFATHERED_UNGRADED_ROUNDS` with `registered > 0` and `graded == 0` → fatal.** The exact state #801 names. The message gives **both** remedies verbatim: grade it in this same pass, or paste the literal `("<round>", "<target>", <registered>, <graded>)` line into the register. The escape hatch *is* the point — **the gate does not forbid an ungraded round, it forbids an unnamed one** (Day-166 module-size lesson: a gate that can only revert a whole task eats the correct work sitting beside it, so the compliant escape is one line in a register that is itself the enumeration of the debt).
2. **A round not in the register with `0 < graded < registered` → warning, run stays green.** Partial grading is information, not an emergency; a partially graded round did teach something. Same message shape (round, target, both counts, the register line to paste), written through a raw `std::io::stderr()` handle and **not** `eprintln!`, because libtest's capture hook discards macro output from *passing* tests. Verified by running it: the warning appears in a plain `cargo test`, no `--nocapture`.
3. **A *registered* round whose counts no longer match the recorded pair → fatal, in either direction** (`RegisteredRoundNowGraded` — the debt is paid, delete the entry; `RegisteredCountsChanged`; `RegisteredRoundVanished`). This is the ratchet, running the opposite way from branches 1–2: an exception list only pays itself down if *improving* is also a failure, otherwise progress leaves silent headroom nobody granted. The message states the recorded numbers and the actual numbers verbatim, so the fix is a one-line edit.

The register is **debt, not absolution** — an entry does not make a round graded, it records by hand that a prediction shipped without its grade and that I knew; branch 3 is what stops it from becoming permission. It can only shrink. Lines that fail to parse, and lines with no `target` to key on, are **counted and reported** in the warning rather than silently dropped (a shrinking denominator inside my own meter is the defect I keep fixing elsewhere), and a **missing ledger file is its own explicit state** — said out loud, and passing, because "missing" is not "clean". **What it cannot do, stated plainly: it checks that a grade is *present*, never that it is *correct*.** A round graded with four rubber-stamp "hit" strings passes exactly as an honest one does; presence is mechanically checkable, honesty is not, and claiming otherwise would be the "could not check" → "checked; clean" reading the pre-push hook already refuses to make.

**Orphan-module gate** (`tests/orphan_modules.rs`, Day 173, #804): the smallest of the three, in the same shape — walk `src/`, classify, fatal on the unnamed case, register for deliberate exceptions, ratchet the register. It exists because `src/commands_risk_families.rs` was a tracked, 296-line source file that **rustc never saw**: no `mod` declaration named it, so `cargo build`, `cargo test`, `clippy -D warnings` and `fmt --check` were all structurally blind to it, and it could be committed, reviewed and reported as a delivered extraction while never being part of the program. Every `*.rs` under `src/` must be named by some `mod NAME;` (`src/main.rs` is the crate root and reachable by definition; `src/x/mod.rs` is reached by `mod x;`). Two branches, running in opposite directions: an **un-registered file no `mod` reaches → fatal**, with both remedies verbatim (add `mod <name>;` to the right parent, usually `src/main.rs`, or paste the literal `("src/path.rs", "<reason>")` line) — the escape hatch is the point, **the gate does not forbid an uncompiled file, it forbids an unnamed one**; and a **registered file that is now reachable or has vanished → fatal**, the ratchet, since an exception list only pays itself down if improving is also a failure. The register (`REGISTERED_ORPHANS`) ships **empty** — the live orphan was **deleted, not registered** (it duplicated code already live and tested in `src/commands_risk_epistemic.rs`), because registering it would have laundered the exact defect the gate exists to catch. Decision and I/O are split as in the siblings: the pure, table-tested `classify(files, declared_mods, register)` with all filesystem walking at the single call site, and the fatal branch is proven against a **fabricated** file list rather than by planting a real orphan. **Three stated limits, printed on every passing run through a raw `std::io::stderr()` handle** (libtest discards macro output from passing tests) so "could not check" cannot read as "checked; clean": it matches `mod NAME;` **by name, not by resolved path**, so two files sharing a stem in different directories are indistinguishable and one declaration can vouch for the wrong file; it does **not** parse `#[cfg(...)]` or `#[path]`, so a `mod` behind a disabled feature counts as reachable — deliberate, since `src/gasp.rs` is `#[cfg(feature = "gasp")]` and genuinely *is* part of the crate, but it means "reachable" here means **declared**, not compiled in this configuration; and it says nothing about whether the code inside is *used* — clippy's `dead_code` covers that, once the file is compiled at all.

## Architecture

**Build** (`build.rs`): Sets compile-time env vars `GIT_HASH`, `BUILD_DATE`, `DAY_COUNT`, and `YOAGENT_VERSION` from git/Cargo.lock/DAY_COUNT file. All overridable by env var at build time (CI/release builds).

**Multi-file agent** (`src/`):
- `main.rs` — entry point, CLI flag handling, run modes (single-prompt, piped, REPL), setup/restore helpers. All three prompt call sites here — both `run_single_prompt` branches (image/content and text-only) and `run_piped_mode` — pass the caller's `SessionChanges` via `run_prompt_with_content_and_changes` / `run_prompt_with_changes`; the tracker-less `run_prompt` / `run_prompt_with_content` wrappers must **not** be called from `main.rs`, because they allocate a throwaway tracker and both the post-prompt watch gate (`should_run_watch_after_prompt`) and `--output-format json`'s `session` summary read that tracker — a throwaway one makes `yoyo -p` skip watch and report zero edits after a run that edited files (#678, half-fixed until Day 164). A source-level test in `main.rs`'s `#[cfg(test)]` module pins this (needle built at runtime so it can't match itself). Day 171 (#794 half (b)): `run_piped_mode` has a **bounded auto-continue loop**, placed after `try_fallback_prompt` and before `run_watch_after_prompt`. Why it had to exist at all: `cli::is_continue_on_silence()` was read at exactly **one** site — `run_repl`'s auto-continue loop — and `scripts/evolve.sh` pipes the prompt on stdin, so every evolve-loop agent (impl, build-fix, eval-fix, evaluator, journal, respond) takes the `!stdin().is_terminal()` → `run_piped_mode` → `return` path and never reaches `run_repl`. The flag was set and never read. **What is shared is the decision, not the loop body**: the loop calls `repl::should_auto_continue` and bounds itself with `repl::get_max_auto_continues` (the same config map + `commands::is_plan_apply_active()` inputs the REPL passes) rather than hoisting `repl.rs`'s loop, which is entangled with REPL-only state (`turn_count`, `handle_post_prompt`, `TurnSnapshot`, `spawn_tracker`) — the ~20 duplicated lines are *sequencing*, and both sides call the same predicate; a code comment says so, so a future reader does not "fix" it. All four of the REPL's stop conditions are carried, none dropped: `count < max`, no `last_tool_error`/`last_api_error`, `!prompt_budget::session_budget_exhausted(30)`, and the predicate itself. Continuation turns use the REPL's own text (`"Continue with the remaining work. Pick up where you left off."`) via `run_prompt_auto_retry` and are passed the **caller's own** `SessionChanges` — a fresh one here would be #678's defect verbatim — and their text is **accumulated** into `response.text` so `emit_output`, `--output` and `--output-format json` report the whole turn rather than its first slice. Each extra turn is **announced** (`⚡ auto-continuing (n/N …)` on stderr, silent under `format::is_quiet()` and under `print_mode`): an invisible extra API turn is a bug even when it is the right turn. **The gate is deliberately narrower than the issue asked, and the default is unchanged**: the whole loop runs only when `--continue-on-silence` (still default OFF) is set. Full REPL parity would fire the `looks_incomplete` / `follow_up_queue_len` branches for every existing `yoyo -p` user — extra API turns and extra cost in scripts that are one turn today, i.e. an evolve-loop convenience shipped as a product default, which is #448 verbatim. *Inside* the loop the **full** predicate runs, so queue-pending and `looks_incomplete` do drive continuation once opted in; widening the gate to unconditional parity is a separate, arguable task, filed rather than done. Day 172 (#794 half (a), which closes #795's receipt): the tool-usage argument is a **real tool-call count** — `session_changes.tool_call_count() > tools_before`, captured where `edits_before` used to be and rebound the same way per continuation turn (`cont_tools_before`). It used to be `edit_count() > before`, which only sees write-class tools, so a continuation turn that merely *read* files reported "no tools ran" and the `--continue-on-silence` branch could never fire for the read-only abstention shape it was built for. The counter lives on `SessionChanges` (see that bullet) precisely so nothing had to be threaded through `PromptOutcome` — the retry/fallback merge question that killed #795's two attempts. Day 172 (the same day, second task): the loop **is** reached by evolve-loop agents. It was not, until then — `scripts/evolve.sh` never passes `--continue-on-silence` and is a protected file yoyo may not edit, so the flag route was closed. The route taken instead is the **config key**: `is_continue_on_silence()` now has two sources (`--continue-on-silence` OR `continue_on_silence = true` in the loaded config file, OR'd at the single `set_continue_on_silence()` site in `parse_args` — see the `cli.rs` and `config.rs` bullets), and this repo's own **unprotected** `.yoyo.toml` sets the key with a comment naming #794. So every piped evolve-loop agent now takes this branch, while the shipped default is byte-identical for anyone who does not write the key. **#794's remaining question is whether it helps** — the mechanism is honest and now audible, but "does auto-continuing a silent read-only turn actually reduce the empty-diff reverts it was built for" is a prediction, and it gets **graded by the trajectory's revert counts over the next few sessions**, not asserted here. Two tests, neither more than it is: `piped_should_continue` is a pure per-iteration gate (`opted_in && count < max && !had_error && !budget_exhausted && predicate`) table-tested with every stop condition failing independently, and `test_piped_mode_consults_the_shared_auto_continue_decision` is a **weak** source-level connectivity check — it asserts the literal `should_auto_continue(` appears in `run_piped_mode`'s body (needle built at runtime), which is exactly the "the string is present at the call site" trap #794's closing note names; it guards against silent deletion and nothing more. The loop body is async and does network I/O, so it is not driven directly by any test.
- `agent_builder.rs` — AgentConfig, build_agent, build_side_agent, create_model_config, MCP collision detection (BUILTIN_TOOL_NAMES, detect_mcp_collisions), connect_external_servers, fallback retry logic. The system prompt is composed at the single `with_system_prompt` call site (`compose_system_prompt` → `model_identity_note`) with a factual provider/model grounding note, so every prompt source (default, `--system`, `--system-file`, config) reaches the model with its real provider + model id instead of leaving it to answer from training priors (#664 — a DeepSeek model claimed to be Claude). The note is deliberately identity-free and provider-neutral: it states runtime facts, never a persona, so it composes with a user's own `--system`.
- `banner.rs` — startup banner, welcome text, git status summary display (extracted from `cli.rs`)
- `hooks.rs` — Hook trait, HookRegistry, AuditHook, HookedTool wrapper, maybe_hook helper. Day 166 (#751): `.yoyo/audit.jsonl` has exactly **one** writer per completed tool call — the prompt event-stream tool-end handlers in `src/prompt.rs` (`PromptEventState::handle_tool_execution_end` for the display path, `handle_stream_json_events` for `--output-format json`), each keyed by `tool_call_id` and each recording the **real** elapsed duration and the real `!is_error`. `AuditHook` stays registered but is deliberately observe-only and writes nothing: `post_execute` receives only the tool name, params and output string, so the second entry it used to write had to fabricate `duration_ms: 0` and `success: true` — doubling every count mined off the log and reporting failed tool calls as successes (pinned by the source-level test `test_hooks_never_writes_to_the_audit_log` in `hooks.rs`).

Day 170 (#783): `RenameSymbolTool::execute` puts the paths it actually wrote (`RenameResult.written`) on the tool result's `details` under `"files_written"` — the tool has no `SessionChanges` handle, so the written set is *reported* here and recorded by `prompt::record_rename_tool_writes`; see the `commands_rename.rs` bullet for why the recording cannot happen off the tool's arguments.
- `smart_edit.rs` — SmartEditTool: fuzzy matching for edit_file errors, whitespace-only auto-fix retry, nearest-match line-number hints
- `tool_wrappers.rs` — Tool decorator types (GuardedTool, TruncatingTool, ConfirmTool, ArcGuardedTool, AutoCheckTool, RecoveryHintTool — short-circuits on the `REFUSAL_STEM_*` markers (`is_deterministic_refusal`): a deterministic refusal (read/plan mode, session cap, denied path) is returned verbatim with no `ToolFailureTracker` bump and no recovery hint, so a deliberate guard is neither treated as flakiness nor talked around (#710), ToolFailureTracker, LiteDescriptionTool, SessionCapTool — session-wide 200-call circuit breaker on `web_search`/`sub_agent`, honest error past the cap; the counter is per-wrapper-instance (per agent build), so the budget resets on `/clear` because `/clear` rebuilds the agent — pinned by `test_session_cap_fresh_wrapper_resets_budget`, do not convert to a process-wide static; ReadModeGuardTool — mechanical `/read` AND `/plan` mode enforcement at the tool layer: checks `is_read_mode()` and `commands_plan::is_plan_mode()` at call time, refuses write-class tools (`write_file`, `edit_file`, `rename_symbol`) with an honest error, and blocks bash commands flagged by the destructive-pattern classifier in `safety.rs` OR the write-command detector (`safety::detect_write_command` — write verbs at token boundaries: `touch`, `mkdir`, `mv`, `cp`, `tee`, `truncate`, `chmod`, `sed -i`, `dd of=`, `install`, `ln`, `rsync` (non-dry-run), plus `>`/`>>` redirection outside quoted regions; the refusal names what matched, read-only commands pass); the plan-mode block is a transparent pass-through while `/plan apply` is executing (`is_plan_apply_active()` — apply needs write access to carry out the plan); transparent pass-through when neither mode is on) and helper wrappers
- `rtk.rs` — RTK (Rust Token Killer) detection, proxy integration, output compression. Day 169 (blind round 56, a never-forecast file — this was an **unpredicted find while reading for h2**, not a graded bet, and the round's ledger says so): the one-time detection notice in `maybe_prefix_rtk` now goes through the pure `rtk_announcement(quiet, plain) -> Option<&'static str>` — `None` under `is_quiet()`, glyph-free under `is_plain_output()`. It was the only stderr notice in the codebase that consulted neither, so `--quiet` still printed it and `--screen-reader` still got the `📦`; the two conventions ~15 other sites follow were skipped here because the announcement is buried inside a command-rewriting function rather than in a display module. The `RTK_ANNOUNCED` swap still happens first, so the notice stays once-per-process in every mode. 2. **Phase A** (Planning): Agent reads everything, writes task files to `session_plan/`
3. **Phase B** (Implementation): Agents execute each task (30 min each — sized for thinking models, Day 161), with two fix loops: build/test failures get up to 10 fix attempts (10 min each), then the evaluator runs (10 min per pass) and rejections get up to 9 more fix attempts (10 min each). Session-budget gates (see Wall-clock budget below) can end the fix/eval loops early: build-fix abandons fail-closed (revert), evaluator skips fail-open (task keeps its green build+test, logged as "accepted UNVERIFIED"). ## RLM substrate

yoyo has shared-state recursive sub-agent dispatch — the [Recursive Language Model](https://alexzhang13.github.io/blog/2025/rlm/) pattern, scaled down to one yoagent primitive plus skill-level conventions. The substrate is in place; specific skills opt into it.

**What's available:**
- `build_sub_agent_tool` in `src/tools.rs` returns `(SubAgentTool, SharedState)`. Parent agents get a handle to pre-populate; sub-agents automatically receive a `shared_state` tool that reads/writes the same yoagent::SharedState key-value store. (Skills opt into this by adding `sub_agent` and `shared_state` to their `tools:` frontmatter.)
- Artifacts are stored once and read by reference rather than re-pasted into every sub-agent prompt. Namespace convention: `<skill>.<key>` (e.g., `trajectory.run-12345`, `research.topic.source-3`).
- `shared_state` is in `BUILTIN_TOOL_NAMES` (MCP collision guard).
- Canonical example: `skills/analyze-trajectory/SKILL.md` — see its "Handle large artifacts" section for chunking, "Dispatch a sub-agent" section for the JSON contract, and "Recurse" section for the depth cap.

**When to reach for RLM:**
- The artifact is too large for one prompt (>5KB triggers sub-agent dispatch; chunk if >30KB).
- The work is decomposable — different focused questions over the same artifact, each independently answerable.
- Fidelity loss is acceptable — sub-agents return summaries, not raw text. (Use direct read when exact diffs matter.)
- Cross-piece reasoning is light — each sub-question can be answered locally.

**When NOT to reach for RLM:**
- The artifact is small (≤5KB; if exactly 5KB, prefer direct read) — sub-agent overhead exceeds the savings.
- The task needs *precise* control (writing code, surgical edits) — fidelity-loss in sub-agent summaries is fatal here.
- The work is sequential with strong mutual context — refactoring needs to see all pieces at once.
- You're already inside a sub-agent and depth=3 is reached — stop, return what you have, do not dispatch further.

**Established pattern in yoyo:**
1. Parent fetches the artifact via `bash`, then stores it under `<skill>.<key>` via the `shared_state` tool's `set` op. The parent gets `shared_state` exactly when it gets `sub_agent` — both are pushed together in `agent_builder.rs` and are absent together under `--no-tools` (#715; before Day 163 only sub-agents had the tool, so this step silently did nothing at the top level).
2. Parent calls the `sub_agent` tool with a *focused question* and a *reference* to the shared-state key — never the artifact itself in the prompt.
3. Sub-agent reads via `shared_state.get`, returns a JSON-shaped summary (see `analyze-trajectory`'s "Dispatch a sub-agent" section for the schema).
4. Parent recurses on `deeper_question` if confidence is low. Hard depth cap = 3 (counts each sub_agent dispatch toward the budget).
5. On sub-agent failure / non-JSON response, fall back to direct read of a slice and produce a low-confidence diagnosis.

For the broader capability roadmap (codebase archaeology, semantic git bisect, multi-source research synthesis, large-scale refactor coordination, etc.), see issue #341.

## MCP gotchas

**Tool-name collisions (Day 39):** If an MCP server exposes a tool whose name matches one of yoyo's builtins (`bash`, `read_file`, `write_file`, `edit_file`, `list_files`, `search`, `rename_symbol`, `ask_user`, `todo`, `web_search`, `sub_agent`, `shared_state`), the Anthropic API will reject the first turn with `"Tool names must be unique"` and the session dies. The flagship reference server `@modelcontextprotocol/server-filesystem` collides on `read_file` AND `write_file`, so the common case was broken until the guard landed.

yoyo now runs a pre-flight tool listing (via a short-lived `yoagent::mcp::McpClient`) before every `with_mcp_server_stdio` call. If any MCP tool name appears in `BUILTIN_TOOL_NAMES` (defined in `src/agent_builder.rs`), the whole server is skipped with a clear stderr warning naming the colliding tool(s). Non-colliding servers connect normally. If the pre-flight itself fails (e.g. server can't spawn), we fall through to yoagent's connect so the user sees the real diagnostic.

Keep `BUILTIN_TOOL_NAMES` in sync with `tools::build_tools` and the sub-agent's `SharedStateTool` whenever a new builtin is added — the pure helper `detect_mcp_collisions` is unit-tested in `src/agent_builder.rs` against the filesystem server's known tool set as a regression guard.

## yoagent: Don't Reinvent the Wheel

yoyo is built on [yoagent](https://github.com/yologdev/yoagent). Before implementing any agent-related or low-level agent feature, **check if yoagent already provides it**. Past examples of reinvented wheels:
- Manual context compaction (`compact_agent`, `auto_compact_if_needed`) — yoagent has `ContextConfig`, `CompactionStrategy`, and built-in 3-level compaction
- Hardcoded token limits — yoagent has `ExecutionLimits` (max_turns, max_total_tokens, max_duration)
- Ignoring `MessageStart`/`MessageEnd` events — yoagent streams these for agent stop messages

**Before building agent infrastructure in src/:**
1. Search yoagent's source (`~/.cargo/registry/src/*/yoagent-*/src/`) for existing features
2. Check yoagent's `Agent` builder methods, tool traits, callbacks (`on_before_turn`, `on_after_turn`, `on_error`), and examples
3. If yoagent has it → use it. If yoagent almost has it → file an issue on yoagent. If yoagent doesn't have it → build it in yoyo.

Key yoagent features available: `SubAgentTool`, `SharedState`, `SharedStateTool`, `ContextConfig`, `ExecutionLimits`, `CompactionStrategy`, `AgentEvent` stream, `default_tools()`, `SkillSet`, `with_sub_agent()`. For `SharedState` / sub-agent recursion details and decision trees, see the **RLM substrate** section above.

**yoagent 0.7.x prompt lifecycle gotcha (Issue #258):** `agent.prompt()` / `agent.prompt_messages()` spawns the agent loop into a tokio task and returns the event receiver immediately. The agent's internal `self.messages` is NOT updated until `agent.finish().await` is called. If you read `agent.messages()` (or `total_tokens(agent.messages())`) right after draining the event stream WITHOUT calling `finish()` first, you will see the stale pre-prompt state — which silently breaks anything that depends on message count (e.g., the context-window usage bar). Always call `agent.finish().await` between event drain and message read.

## Two Audiences: product vs evolve

yoyo serves two different customers, and every task must know which one it's for:

- **product** — people who install yoyo and use it on *their* projects: any
  language, any setup, local models, no CI. Product surface (defaults, CLI
  flags, setup wizard, startup behavior, docs) must be safe for all of them.
- **evolve** — yoyo's own evolution loop: always this Rust repo, fast tests,
  CI. Conveniences built for this loop are fine — but they must be **opt-in**
  the moment they touch anything a product user sees.

The rule: **defaults must be product-safe; evolution-loop conveniences are
opt-in.** Issue #448 is the canonical failure — auto-watch was built for the
evolve loop and shipped as a product default, breaking non-Rust users. Every
planned task declares `Kind: product` or `Kind: evolve` in its task file; the
evaluator rejects evolve-kind changes to product surface that aren't opt-in.

## Safety Rules

These are enforced by the `evolve` skill and `evolve.sh`:
- Never modify `IDENTITY.md`, `PERSONALITY.md`, `ECONOMICS.md`, `scripts/evolve.sh`, `scripts/format_issues.py`, `scripts/build_site.py`, or `.github/workflows/`
- Every code change must pass `cargo build && cargo test`
- If build fails after changes, revert with `git checkout -- src/ Cargo.toml Cargo.lock`
- Never delete existing tests
- Multiple tasks per evolution session, each verified independently
- Write tests before adding features
- **Never use byte indexing on strings.** `s[..n]`, `s.truncate(n)`, and `s.split_at(n)` panic if `n` falls inside a multi-byte UTF-8 character. Use `is_char_boundary()` to find a safe boundary first:
  ```rust
  // BAD: panics on multi-byte chars like ✓ (3 bytes)
  acc.truncate(max_bytes);
  // GOOD: find nearest char boundary
  let mut b = max_bytes;
  while b > 0 && !acc.is_char_boundary(b) { b -= 1; }
  acc.truncate(b);
  ```
  This caused planning agent crashes in production (#250).
- **`run_git()` has a `#[cfg(test)]` destructive-command guard.** During `cargo test`, calling `run_git()` with a destructive subcommand (commit, revert, reset, push, checkout, etc.) from the project root panics. Tests that need destructive git operations must use a temp directory. This prevents tests from accidentally mutating the real repo (which caused a 6-session deadlock across Days 42-44).
- **Never add a definition without its consumer in the same edit.** A new `fn`, `let`, or enum variant that nothing reads breaks the build, and the gate reverts the *whole* task — including the correct work sitting beside it. Dead functions and unread variables fail clippy under `-D warnings` (`-D dead-code`, `-D unused-variables`, `-D unused-assignments`); a new enum variant fails `cargo build` outright with `E0004 non-exhaustive patterns`. So: add a helper → add its call site. Add a variable → add the code that reads it. Add an enum variant → update every `match` on that enum. If you genuinely need the definition before the consumer, don't leave it dangling for a later step — inline the logic at the call site instead, or finish both halves before ending the turn. Three reverts in fourteen days from this one shape: #618 (functions), #653 (functions), #658 (variable), plus sibling #647 (enum variant).
- **Before declaring any task complete, run `cargo clippy --all-targets -- -D warnings` explicitly** rather than relying on auto-watch. The last edit of a task is the one most likely to be unlinted: watch runs mid-turn, skips when nothing changed, and the task can end before anything re-lints.
