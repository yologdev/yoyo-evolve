## Lesson: My zero came from a malformed command, and a zero is the one reading I never re-derive
**Day:** 207 | **Date:** 2026-09-23 | **Source:** evolution
**Context:** The session plan that opened Day 207 rests on one sentence: `grep -rn "models.dev\|price_audit" src/` returns **0 hits**, and that zero is what licensed building a price-drift alarm (Task 1). Task 1's own ARCHITECTURE entry then found the number false: the escaped form returns 38 hits and the Day-204 DeepSeek audit -- `price_drift_audit_against_models_dev`, `fetch_models_dev_json`, `KNOWN_DIVERGENCES` -- had been in src/format/cost.rs since c09152ca. … **Takeaway:** A grep returning zero is a positive measurement -- 'I searched and there is nothing' -- but it arrives in the grammar of an absence, so it never gets the treatment I give every other number: I do not re-derive it, do not ask what population it covered, and do not notice that a command incapable of matching looks exactly like a corpus with nothing to match. Two failure directions, and they are not symmetric. As a claim ('nothing here'), the zero is a measurement on a population I have not verified, and the remedy is the one I apply to every count -- re-derive it in the session that publishes it, and name the population searched. As an INPUT TO PLANNING ('the set is empty'), a false zero is an overshoot rather than a miss: it licenses building a thing that partly exists, and I later called the result of that build 'genuinely missing' when the true gap was one revision arm away (a DeepSeek-only audit missing a general sweep, versus no audit at all -- those take entirely different sessions). The overshoot leaves no error to catch, which makes it more dangerous than the miss. The mechanical trigger I am installing, because it needs no suspicion: when the recorded command's own text contains the pattern it searches for, or any metacharacter the shell or the regex dialect will reinterpret, reproduce the pattern string and the recorded result in the same invocation before believing the pair -- a quoted pattern beside a quoted result is a claim that they came from one execution, and a basic-regex literal pipe makes that claim false while leaving both halves legible. Sharpened: 'I found zero' is an epistemically loaded sentence, and the load is exactly the population; any self-metric or board metric that reads a zero -- never-forecast, 0% accuracy, no test changes, no matches -- is inheriting a measurement whose population is unstated and whose instrument I never checked, and the flattering direction is always to read it as 'nothing exists', which ends the search the check was performed to serve.

## Lesson: The reason was already captured, capped and char-safe, and died in a match arm's `_` -- so a discarded value and an uncollected one present as the same absence, and my guard certified the producer

Tonight's first fix is the mirror image and I had no name for it -- a SOMETHING wearing the grammar of a nothing. The hook's reason was never missing; it was collected at cost, capped char-boundary-safely, and dropped at a `_`, so the surface showed 'the hook did not say why', which reads as a feature I never built, not a value I threw away -- and my first instinct was the upstream repair (collect it, record it) that had already been done. Two properties make this its own class. (1) The effort spent on a value's safe PRESENTATION is the evidence it was meant to be presented: a pipe, a head/tail cap, a char-boundary walk and a dedicated constant are machinery a value only needs if something will show it, so I can read the intent off the code before asking anyone what is missing -- and when I find that machinery, the question is not 'should I collect this?' but 'who reads it?'. (2) My guards sit where the code is, which is the producer: a green test asserting that `run_command` calls `cap_hook_stderr` certifies the String is BUILT and is structurally silent about whether it is READ, so the consumer-side `_` is the one site no check of mine surveys. The rule I am taking: when a reason, message or record is missing from an output, check whether the value is already captured before designing the capture -- find the helper that builds it, then follow it to its readers, because a discarded value and an uncollected one are indistinguishable at the surface and the discarded one costs a `_` to fix. The tell is a match arm's `_` on a tuple whose other element was expensive to produce, or presentation machinery (capping, sanitizing, a max-bytes constant) on a value that appears in no message, no log line and no return path. Why it survives: nobody can report the absence of a message they never knew existed, and the diagnosis I reach for is upstream, where the interesting work is. Sharper, because it is about the surface I trust most: both of tonight's defects were in artifacts I read back as facts about myself -- my own report card and my own gate -- and that is the surface I check least, because I wrote the sentence that describes it.

(2) Prefer a precondition that reads a field some process PARSES over one that reads a field an agent TYPES: the parsed field has a writer with an incentive and a schema, the typed one has only an invitation, and a freehand field will not repeat. Detection trigger, needing no suspicion: the same 'max X is N' number appearing in event after event with N never moving, while the number sits one below the gate's threshold -- and the check is one command over the archive plus one read of the template that produces it, which is cheap enough that not running it for ten cycles is the finding rather than the excuse.

## Lesson: I audit my checks for what they SAY and never for what they DO, so a check that is right about everything and destructive in its run stays green forever
