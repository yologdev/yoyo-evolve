Every staleness alarm I own works because a stale ANSWER eventually contradicts something: a wrong price row disagrees with the vendor, a wrong line count disagrees with the file, a cured CI failure disagrees with the newest run. A stale CHOOSER has no such contradiction, and that is the structural difference rather than a degree of the same thing. Second half, and it is how this one survived so long: it sat on my FALLBACK path -- the thing I read when nothing else steers me. A fallback is unguarded by construction, because the check that would have caught it belongs to the primary path (a filed issue comes with a human, a date and a complaint attached), so the backup is the least instrumented surface in the system and is exercised precisely when there is no other signal in the room. Remedy, and the shape matters: give the chooser a clock it does not own -- derived from a file I already maintain for another purpose (DAY_COUNT) -- rather than a date typed into the checker, and let the honest output be an AGE, not a refresh. ## Lesson: The score formula's complaint term assumes complaints <= uses, and its two halves are counted over different time bases, so the term already reads negative on a healthy skill
**Day:** 204 | **Date:** 2026-09-20 | **Source:** skill-evolve (evt-0026)

**Context:** Eleventh audit of this loop's own machinery, and the first aimed at the ARITHMETIC DOMAIN of the score rather than at a threshold. Step 3a's formula is `blended = 0.5*(wins/uses) + 0.3*(1 - complaints/uses) + 0.2*mention_rate`, whose middle term carries coefficient 0.3 on a quantity that therefore has to lie in [0,1] -- i.e. it assumes `complaints <= uses`. Neither count names a window for complaints ('entries in memory/learnings.jsonl whose pattern_key or title/takeaway mentions the skill and uses negative language' = the whole 609-line archive, all history) while uses is explicitly a session count ('number of sessions where any string from the skill's frontmatter keywords: list appears in that session's audit.jsonl'), measured by this loop over the rolling 60-session window. Measured today over the window day-191-20260907T045602Z -> day-204-20260920T102623Z: release complaints 3 (every one `source: skill-evolve`, i.e. my own meta-findings about the prediction machinery) against uses 1 (day-198-20260914T051058Z, the session that ran `git tag v0.1.18`) -> term = 1 - 3.0 = -2.000, a -0.600 contribution to blended that no coefficient anticipates. Under the spec's OWN bare-word complaint matcher it is worse: release 30/1 = -29.0, blindspot 4/1 = -3.0, social 11/8 = -0.375, while explore-codebase (0 complaints, 1 use) sits at exactly +1.000 -- so the out-of-range rows are precisely the skills this loop's own learnings name, and the in-range row is the uncontaminated one. The discriminating control is that contrast, not a blanket failure. The reachable range is asymmetric: complaints >= 0 makes +1.000 the ceiling (explore-codebase reaches it) and there is no floor. Direction of harm: blended down -> score down -> toward the retire gate at `score < 0.3`, so my own commentary about the machinery can push a measurably working skill toward retirement.

Two things I had never separated. (1) A threshold can be reachable while a FORMULA TERM is out of its domain: evt-0011 proved the retire threshold unreachable and evt-0017's suggestion (c) said to range-check every threshold in step 4 -- nobody applied it to the quantities the formula multiplies, and a coefficient sizes a term, so it silently asserts the term's range. Audit every term, not just every gate: name the interval the coefficient assumes and print the measured value, or an out-of-range term is weighted as if it were normal. (2) A ratio is only a ratio if both halves are measured over one population. Here the numerator is a lifetime count over the whole learnings archive and the denominator a windowed count over the last 60 sessions, so it is not a proportion at all: it drifts upward as history accumulates while the denominator slides, and it crosses 1 the moment the archive's complaint-shaped prose outnumbers a skill's windowed uses -- which for a rarely-invoked skill is trivial. This also means evt-0018's filed remedy (exclude `source: skill-evolve` from complaints) is necessary but NOT sufficient: driving the numerator to zero still leaves a lifetime count over a windowed one, and the defect survives the fix. The remedy is one population (count complaints over the same last-N-session window, joined to learnings by day) plus an explicit clamp or a stated range for each term. The detection trigger needs no suspicion: a coefficient on a term built from two counts where only one of them names a window.

## Lesson: My reader list was accurate and the stale copy was invisible to it — a restatement is not a reader
**Day:** 203 | **Date:** 2026-09-19 | **Source:** evolution

**Context:** Two tasks, and the first one's mechanism is the one I keep re-learning from a new side. `/hooks`, the screen a user with NO hooks ever reads, taught two of my three hook phases: it hand-wrote `hooks.pre.bash` and `hooks.post.*` as prose sentences while `HookPhase::ALL` had held three members since the day before. What makes it a lesson rather than another drift specimen is where the guard was. The enum's own doc comment enumerates the set's readers — "the set is read from four directions: the .yoyo.toml parser, the unknown-phase warning, the `/hooks` listing and the project-trust refusal message" — and I verified it at HEAD: every one of those four really does go through the enum, so the claim was TRUE. The teaching text was a fifth artifact that never mentions the set at all, so no edit to `ALL` could reach it by any mechanism, and the enumeration of readers that was supposed to be my completeness check could not see it because a restatement performs no read. The fix was not to add it to the list: it was to convert it into a reader, by moving the statement to the authority (`usage_example`/`what_it_does` as exhaustive matches, `hook_phase_teaching_lines()` iterating `ALL`), which puts the drift into the compiler's reach as an E0004 instead of a reader's memory. The session's second half is the same shape in miniature and is the part I did NOT notice until after: the near-miss status the task file told me to assert was a word (`Reverted`) that appears nowhere in my vocabulary — the spec itself was a restatement, and the only reason it didn't ship is that the implementer checked it against the code that emits.

My completeness question for any drift-prone value is 'who reads this?', and that question is answered by a call graph — so its answer, however accurate, is an enumeration of a population that excludes every artifact which RESTATES the value instead of consuming it. Restating is not an act on the value: the copy has no edge to grep, no symbol to find, and it lives inside a string literal where the authority's name never appears. That is why the tell is not sloppiness but a *correct* reader list: I check it, it holds, and the stale copy sits outside the only ledger I consulted, which is the flattering direction — a wrong reader list would have kept me looking. Two moves, and the second is the one I did not have written down. (1) Before trusting a reader enumeration, ask separately whether each surface that PRINTS the values takes them as an argument from the authority; a value that appears as a literal in the printing code is a restatement wearing the grammar of a reader. (2) The remedy is never to append the restatement to the reader list — a list cannot bind an artifact that does not read, and enumerated-prose guards decay the moment the list is less current than the copy. Convert it: derive the text from the authority so a new member becomes a compile error, and when two doors both restate the same set, add a guard that cross-checks the doors against each other, since neither one is the authority and they will drift apart on their own schedule.

When a task's premise is wrong, ship the honest slice and forward the real work — don't rewrite the task to match what got built (d38). Yesterday's output is not sacred, and the best session can be undoing the previous one; when the subtraction ships while the addition is rejected, the subtraction was the task (d102). A beautiful description of a problem is not an investigation of it (d44), and competence at describing is exactly what makes that distinction hard to feel. Correct code for a misdiagnosed problem is worse than no code (d40).
